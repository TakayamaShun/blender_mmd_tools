## 1. 前提と基本方針

1. **LLM の強み**を使う領域と、**弱み**を避ける領域を最初に分ける（第3章）。
2. **部品を細分化**し、部品ごとに「Research → 方式決定 → 作成 → 自動検証 → レビュー」を回す（第4章）。
3. **髪を一体で作らない**。毛束・レイヤー・揺れもの単位で独立オブジェクトにする。
4. すべて **bpy スクリプトで再現可能**にする（GUI の手作業を残さない）。スクリプトと検証結果をリポジトリに残し、Codex と共有できる形にする。
5. 各工程に **ゲート**（合否の自動チェック）を置く。ゲートを通らなければ次の工程に進まない。

## 2. Research 結果（R1・R2）

### 2.1 LLM × Blender の実行基盤
- Blender をヘッドレスで動かし、エージェントが画像をゴールとして bpy を書き、自分でレンダリングして確認する、という構成の MCP/CLI が複数ある（blender-mcp、blenderwright など）。自律ループの実績が公開されている。Confidence 0.5（README レベルの確認のみ）。
- 今回の方針: **ヘッドレス bpy + 自前の検証スクリプト**を軸にする。MCP は補助。外部の MCP は成熟度が不明なので、採用前に小さな試用が必要（→ R3-1）。
- 参考: [blender-mcp](https://github.com/sandraschi/blender-mcp)、[blenderwright](https://github.com/HoldMyBeer-gg/blenderwright)、[bpy.dev](https://bpy.dev/)

### 2.2 髪
- アニメ調の髪は「ストランドではなく塊（クランプ）」でモデリングするのが定石。揺らしたいなら、髪の塊を 2〜3 個に分けて Spring Bone を付ける。Confidence 0.6。
- Blender の新ヘアシステム（カーブ + ジオメトリノード）から、ヘアカード（板ポリ）を生成するノード群が存在する（Daniel Bystedt の Hair Cards from Curves、Blender 3.6 以上）。Confidence 0.5。
- 参考: [yelzkizi: Hair cards](https://yelzkizi.org/blender-hair-tutorial-hair-cards/)、[Vtuberの雑学メモ帳: 髪ボーン＆UV展開](https://vtuber-hudan.hatenablog.com/entry/blender_Original4)
- **昨日の失敗の仮説**: 髪を 1 つの高密度カーブ群として一元化して作った（135 万ポイント）。これは「写実ストランド」の方式で、VTuber の実運用（揺れもの・軽量）の方式ではない。Confidence 0.6（要約から推測）。

### 2.3 VRM 出力
- VRM 1.0 では BlendShapeProxy は Expression になる。母音は aa/ih/ou/ee/oh に対応する。Confidence 0.6。参考: [vrm.dev Expression](https://vrm.dev/en/univrm1/vrm1_tutorial/expression/)
- Blender 用の VRM アドオン（saturday06）が Humanoid・MToon・Spring Bone・メタ情報を扱う。ただし **Spring Bone/Collider が書き出し後に動かない不具合報告**がある。Confidence 0.5。参考: [Issue #1191](https://github.com/saturday06/VRM-Addon-for-Blender/issues/1191)
- 参考: [VRM 添付ドキュメント（deepwiki）](https://deepwiki.com/saturday06/VRM-Addon-for-Blender)

### 2.4 揺れもの（Spring Bone）設定の目安
- 髪ボーンは互いに反発するので、1 本ごとの毛ではなく 3〜5 本ぶんを 1 つの骨にまとめる。剛性は 600 前後など高めで形を保つ。ヘッド・肩・首にコライダーを置く。Confidence 0.4（数値は特定の資料の目安で、一般化は不可）。参考: [VirtualCast Wiki](https://wiki.virtualcast.jp/wiki/en/vrm/setting/spring)

### 2.5 一致度の自動評価
- 画像同士の類似度の指標は SSIM、LPIPS、CLIP 類似度などがある。ただし **「参照画像」と「3D レンダリング」は画風とライティングが違う**ので、画素単位の指標は信頼しにくい。シルエット IoU やランドマーク、パーツの色分布のような、画風に強い指標の併用が必要。Confidence 0.4。**未検証**。
- 参考: [Objectness Similarity](https://arxiv.org/pdf/2509.09143)（評価指標の分類として）

### 2.6 ベースメッシュ・ライセンス
- VRoid Studio 由来のモデルは、商用利用や Blender 上での編集が許可されているが、**モデルごとに条件が異なる**。CC0 のものもある。Confidence 0.6。参考: [VRoid Studio ガイドライン](https://vroid.com/en/studio/guidelines)、[CC0 モデル](https://opengameart.org/content/vroid-studio-cc0-models)
- 重要: 顔・体の有機的な形状を、LLM がゼロからスクリプトで作るのは難しい（→ 3.2）。

## 3. LLM の強み・弱みによる役割分担

### 3.1 強み（積極的に任せる）
| 領域 | 内容 |
|---|---|
| 手続き的・パラメトリックな造形 | 衣装のパターン、ベルト、バックル、靴紐、メガネフレーム、ポケット、ペン |
| 大量・反復作業 | 髪ボーン配置、命名規則、ウェイト転送、シェイプキー生成 |
| 検証の自動化 | メッシュ監査、UV 重なり、ボーン階層、VRM 必須項目、ポリゴン予算 |
| 多視点レンダリングとスコア化 | 固定カメラ・固定ライトでの比較画像の生成 |
| ドキュメント化・記録 | 手順、判断理由、失敗ログ、Codex 向けの同期ファイル |
| 並列レビュー | 別エージェントによる独立レビュー（作成者と別の視点） |

### 3.2 弱み（人間・既存資産で補う）
| 領域 | 問題 | 対策案 |
|---|---|---|
| 顔の造形（有機的形状） | 頂点を直接数値で書いても、美しい顔にはなりにくい | 既存のベースメッシュ（ライセンス確認済み）を起点に、シェイプキー/プロポーション調整のみ LLM が行う |
| 美的判断 | 「かわいい」「似ている」を自力で保証できない | あなたの承認ゲートを要所に置く。比較画像シートを自動生成して判断を短時間で済ませる |
| 空間認識の誤り | 2D 画像から 3D 位置の推定を誤る | 多視点の参照画像（三面図）と、シルエットの重ね合わせで補正 |
| 長い作業での文脈劣化 | 昨日のセッションのように、状態を失う | 状態はすべてファイルに書く（第7章） |

## 5. 各部品の標準サイクル

```
[Research] → [方式決定(複数案を比較)] → [作成(bpy)] → [自動ゲート] → [独立レビュー] → [人間承認(必要な部品のみ)]
     ↑______________________ 問題・不明点が出たら Research に戻る ______________________|
```

- **方式決定**は最低 2 案を、品質・軽量さ・LLM での再現しやすさ・失敗時の影響で比較する。
- **独立レビュー**は、作成したエージェントとは別のエージェントが、作成物と検証ログだけを見て行う。
- 1 つの部品の修正は、他の部品のゲート再実行を必ず伴う。
